# Reelay

Where films and series stream in Sweden. A web app people add to their iPhone Home Screen (not an App Store app). Personal project: free, no ads, sign-in by email code only, no browsing without an account.

## Where the design lives

- Design canvas (screens, components, tokens): https://claude.ai/artifact/1Fo2PjsKmhJqA3Uiq76i35 — build only what is on the **Current** page. The In progress page is exploration.
- Design decisions doc (rules, open questions, decision log): https://claude.ai/artifact/3sRRqQPxj8P8R3RvcATcSx — start with its Handoff overview.
- `docs/build-notes.md` — the build notes from beside each Current screen.
- `public/brand/wordmark.svg` — the Reelay wordmark as outlines (Inter Display SemiBold, -0.02em), `fill=currentColor`, one `<path class="l">` per letter for the Start rise. Always use it instead of typing “Reelay” in the font. `wordmark-email.png` is the black version for emails (email apps don’t show SVG).
- Poster corner marks: the services' own logos, small white versions in `src/assets/marks` (made from `public/icons/services/logos`, 36 px tall, 16 shades of transparency, inlined: about 9 KB), sized in `ServiceMark` by one optical rule (`markSize`, `MARK_SHAPE`: about the same box area for every logo, a little larger for thin light ones (area ∝ 1/√ink), 6.5–11.5 px tall, at most 34 wide; a new logo gets its ratio and ink measured from its file). SVT Play and SkyShowtime (their own wordmarks in `public/icons/services/`) follow the same rule; TV4 keeps 10 × 10. A service without a logo (hayu, Cineasterna, Draken Film) shows its name in 7 px semibold. `public/icons/ui/laurel.svg` — the award laurel.
- `public/fonts/` — self-hosted Inter (from rsms.me, opsz 32, weights 400–700) and a Material Symbols file with only our icons, declared in `src/styles/fonts.css`. Never load fonts from Google or another CDN (GDPR). New icon: add its name to `scripts/fonts/icons.txt`, run `scripts/fonts/build-icons.py` (instructions at the top of the script) and raise the `?v=` on the icon font in `src/styles/fonts.css` and its preload in `index.html` (phones keep the font a week, and an icon missing from the old file shows as its name).
- `src/styles/tokens.css` — every colour, type style, size, radius and motion value. Use the variables; don't hard-code values.

## Stack

- Vite + React + TypeScript, deployed on Vercel from `main` to https://usereelay.vercel.app.
- Testing branch: `sprint-2` is the one staging branch (decided 20 Nov). New work is pushed there so its preview URL stays the same: https://reelay-git-sprint-2-kunwaryanto.vercel.app. Merge it into `main` when a round is approved, through a pull request from sprint-2 (the REST API: `gh api repos/Kunwaryanto/Reelay/pulls -f head=sprint-2 -f base=main …`, as `gh pr` needs GraphQL): the `Browser tests` workflow runs on it, and it is merged (`…/pulls/<n>/merge`) only when they pass, never by pushing a merge to `main`. A Home Screen install can't be reloaded by hand, so the app notices a new deploy itself: a white dot by the Settings cog on Now, an Update card at the top of Settings, and a Version row under About that shows the build (commit) and opens a page where you can check for an update and apply it.
- Supabase (database, auth with 6-digit email code). Everything Supabase is in `supabase/`:
  migrations in `supabase/migrations`, auth settings in `supabase/config.toml`, email template in `supabase/templates`.
  The `Supabase migrations` workflow applies new migrations when they reach `main` (`supabase db push`); `Supabase status` lists what's applied. Never change the database by hand in the dashboard; add a migration.
  Invite only: open sign-ups are off; `supabase/functions/redeem-invite` creates the account from an invite link (`invites` table, `create_invite`/`cancel_invite`/`restore_invite` RPCs for admins, `profiles.is_admin`). The `Make admin` workflow makes someone an admin. Edge Functions deploy with the `Supabase functions` workflow.
  Letterboxd (staging since 22 Nov): a member types their username in Settings › Letterboxd; `supabase/functions/letterboxd` checks it and reads their public diary feed (`letterboxd.com/<name>/rss/`: films with TMDB id, date, rating, rewatch; latest entries only), and the nightly sync reads every connected member again. `letterboxd_accounts` and `letterboxd_logs` are written only by the server and readable by everyone signed in (the same things are public on Letterboxd); the owner can switch off greying their seen films on posters or disconnect, which deletes their rows. Ratings are shown as numbers out of 5. Older history comes from the member's Letterboxd export: the app opens the ZIP on the phone and sends only the film rows to `supabase/functions/letterboxd-import`; imported rows are kept by film name and year and matched to the catalogue by `letterboxd_resolve` (at import and nightly), which also drops rows the feed already has.
  Home (`src/lib/home.ts`) is built per member: their services, their watchlist and their Letterboxd. It needs `titles.trend_rank` (TMDB's weekly trending, nightly), `title_recs` (TMDB's recommendations for films members rated 4+), and the functions `home_because`, `home_friends` and `home_taste`. The `Home data` workflow runs those sync steps by hand. Home is built again only when the sync's `data_stamp` moves (every sync run sets it), the day turns, or the member's watchlist or Letterboxd films change; never while the member is looking at it (`src/lib/homeData.ts`). A phone with no Home saved (a first sign-in, a new phone) shows a quick Home first: the rows everybody gets (trending, new on their services, leaving soon, new films and series) from `home_base` (migration `20261125001700`: built per set of services, kept until the next sync or day, one request; the nightly sync makes it ready for every member's set through `refresh_home_bases` after setting the stamp), fitted to the member on the phone (`loadHome(ask, { quick: true })`, `partial`); the whole Home is built meanwhile and waits out of sight like any new Home. Under the hero, watchlist news (`news` in `loadHome`, `News` in Now.tsx): one line, no card, for saved titles that arrived on the member's services in the last 14 days or leave within 14; there is no watchlist row. An arrival leaves the line once seen (its title page opened, or the line tapped to open Watchlist; `src/lib/newsSeen.ts`, on the phone only), something leaving stays until it leaves, a logged film goes.
  Awards (`awards`): Oscars, Primetime Emmys and Golden Globes from Wikidata, wins and nominations, also those given to a person for a title. `syncAwards` finds each award's categories with Wikidata's label search, then every statement in them, matched to our titles by `wikidata_id`; the table is rebuilt whole on Sundays in the nightly sync, or by hand with the `Awards` workflow (dry run option). Home shows one award row a day, taking turns (Oscar winners, Emmy-winning series, Best Picture winners, Golden Globe winners), with the top category under each poster ("Best Picture +3").
  More like this (title page): `title_similar` holds up to 15 alike titles per streaming title, built nightly (TMDB recommendations first, then `similar_backup`'s scoring); the app reads it through `similar_titles`, which scores live for a title without a list. The member's order (their services first, logged films left out) is put on in `Title.tsx`.
  Beyond what streams: well-known titles (500+ votes on TMDB, `titles.notable`) are kept whether or not they stream (`syncNotable`, Sundays and the `Notable titles` workflow; never cleaned up). Everything else on TMDB is found through `supabase/functions/tmdb` (needs the `TMDB_READ_TOKEN` function secret, set by the functions workflow): Search shows TMDB's titles the catalogue lacks after its own results (name words only, not with a service or "my services"), and opening one saves it first (`save_tmdb_title`, kept as 'searched', cleaned up after 90 days unless it streams, is saved, notable or has awards).
  Search (`search_titles`, migration `20261124000900`): words that start with what was typed (a word index on `search_text`, works from one letter), then contains (three letters on), then near misses (four on); exact names first, then streaming, then fame (TMDB popularity plus IMDb votes); services are looked up only for the titles returned. `search_text` holds the title, original, English title and `aka` (other names in Sweden: the Swedish title and TMDB's Swedish alternative titles, written by the sync; `Other titles` workflow to fill them all again). Nordic originals (Swedish, Danish, Norwegian) are shown by their original title: a trigger (`titles_nordic_name`) keeps TMDB's English one in `title_en`, which search and Letterboxd matching also use.
  Title page picture (`titles.hero_path`, `hero_poster`): chosen by the sync from all of TMDB's images (`heroOf`): a textless poster (shown at 780 wide, framed from the top), else the best textless backdrop at least 1920 wide (shown at full size, so the tall crop stays sharp); empty falls back to the backdrop, then the poster (`titleHero` in pictures.ts). `Title pictures` workflow to choose them all again.
  Suggestion preferences (Settings › Suggestions, `src/lib/hidden.ts`): `profiles.hidden_tags` holds what a member doesn't want suggested, matched against `titles.tags`, a stored column made by `title_tags()` from genres, countries, language, IMDb votes and rating and `titles.standup` (migrations `20261125000100`, `…0200`): one tag per genre plus `kids` (TMDB's Kids genre, or animated family titles under 50,000 votes, or under 10,000 rated 7.0+), `anime` (animation from Japan) and `standup` (TMDB's "stand-up comedy" keyword, read by the sync on Sundays and the `Stand-up` workflow). Changing `title_tags()` needs the column dropped and added again (it is stored). Home, Browse (its queries, and categories all about a hidden tag), Explore, Search's ideas and More like this use `suggestable`/`shown` with the list; searching by name, the watchlist and its news don't. Saved lists built with tags hidden carry `hiddenKey()` in their name. The list is kept on the phone too, so the first screen knows it.
  Fame (`titles.fame`, stored and indexed, migration `20261125000300`): ln(1 + TMDB popularity) + 0.4 × ln(1 + IMDb votes), how well known a title is (popularity alone follows this week's clicks). Both walls are what a film enthusiast would pick (`wall_part`, migrations `20261125000400` to `…1500`), three films for every series: films in even thirds: new (last 5 years, Letterboxd 3.7+), the modern canon (1980 to 20 years ago) and the old canon (before 1980), both Letterboxd 4.0+ with 25,000+ IMDb votes; and new series (last 5 years, IMDb 8.0+, 90%+ from critics on Rotten Tomatoes and an Emmy or Golden Globe nomination in `awards`), each best rated first (the modern canon by Letterboxd rating minus 0.15 × ln(1 + votes / 25,000), so the less obvious come before the films everyone has seen); one film per series (`titles.collection_id`, TMDB's collections: saved by the sync, filled in once by the `Film series` workflow), all with 20,000+ IMDb votes; in an 8-step pattern (new, canon, old, series, new, canon, old, series); never kids, stand-up, concert films (music with no story genre) or films under an hour; anime (rated very high by fans) at most 4 on onboarding's wall and 3 on Start, the best rated. When the walls' content changes, raise `WALL_VERSION` in PosterWall.tsx so phones drop their saved wall. The Start wall (`refresh_start_wall`, nightly, 48 posters) takes the best of all; onboarding's wall (`onboarding_wall`, one request, read by `loadWall`) takes each service's best, and a slot falls back to another part of the mix, then another service. The onboarding wall is 8 × 8 (64 to pick from): Services and Notifications frame the middle 6 columns, the wall waits only for the middle 36 posters, and the outer ones load once Services is up (`inner`). The wall is one module, `src/screens/PosterWall.tsx` (`useWall`, `useWallPan`, `WallColumns`): onboarding and the empty Watchlist (`PickWall`, the member's services, at onboarding's Pick camera) both use it, so a change to the wall changes both; don't build a wall of posters anywhere else.
  Catalogue tables are readable by signed-in users only and written only by the sync; user tables (profiles, user_services, watchlist, push_subscriptions, invites) are private to their owner via RLS.
- Secrets live in GitHub Actions secrets (`SUPABASE_ACCESS_TOKEN`, `SUPABASE_PROJECT_REF`, `SUPABASE_DB_PASSWORD`, `BREVO_SMTP_LOGIN`, `BREVO_SMTP_KEY`, `BREVO_SENDER_EMAIL`, and for notifications `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`) and Vercel env vars (`VITE_VAPID_PUBLIC_KEY` is the same public key). Never commit them.

## Browser support

- **Target: Safari on iOS 26 and later**, as a Home Screen web app, and in Safari for Start, sign-in and invite links. Any feature that Safari on iOS 26 supports may be used without a fallback, even if it isn't Baseline Widely available.
- Features Safari doesn't support may only be used as progressive enhancement that falls back to the designed look (e.g. `corner-shape: squircle` falls back to ordinary rounded corners). No polyfills.
- Other phones (Android, Chrome) can use Reelay too, best effort: nothing may block them, but we design and test for iPhone.
- Exception: the "Made for your phone" desktop page must work in current Chrome, Edge, Firefox and Safari (Baseline Widely available).
- Front-end work uses the `modern-web-guidance` skill (`.agents/skills/modern-web-guidance`, from Google Chrome). Apply its guides with the target above; it does not apply to the sync, database or CI.

## Rules

- Dark only. One grey (#808080) for meta, faint text and every inactive icon.
- Inter at opsz 32; Material Symbols Outlined weight 250, 24px.
- No sharing of titles (dropped 20 Nov: links can't open the Home Screen app). Reelay is invite only: admins create single-use invite links in Settings.
- iPhone web app limits: links always open in Safari (or the service's own app, for its https links when it's installed), Safari and the installed app don't share storage, no background sync, no haptics.
- Sheets: `Sheet` (in `src/ui`) draws itself in `#root`, so it always covers the tab bar and opens from the bottom. Never wrap a sheet in `createPortal`: on the body, iOS scrolls the document when the sheet takes focus and it opens at the top of the screen.
- Fields: a tap on a text field is focused by the app itself without scrolling (`guardFieldTaps` in `src/lib/keyboard.ts`, installed once for every field), so iOS never jumps the page when the keyboard opens. Don't add per-screen versions; a field that moves with the keyboard itself opts out with `data-own-focus`.
- The first tab is called **Home** (renamed from Now on 22 Nov). In the code it is still `now` (`src/screens/Now.tsx`, the `now` tab id), and older notes say Now.
- History: in the Home Screen app the app keeps one history entry (`ONE_ENTRY` in nav.tsx), so iOS's own edge swipe back never appears; going back is the app's swipe and back button. In a browser, pages are history entries.
- Routes: every address is in `src/lib/routes.ts`: `routeOf` is the only code that reads a path and `paths` the only code that builds one (never write `/title/${id}` by hand). A new page is a new route there, its screen in `renderRoute` (App), and what it loads in `pageOf` (pages.ts); whether the tab bar shows is `tabBarShown`.
- Page frame: a page with an entry reads it through `usePageFrame` and shows `PageContent` inside its `<main data-arrive={frame.arrive}>`: placeholders, Couldn't load, the page's `missing` state and the fade-in are the same everywhere. Don't write them per page.
- Saved content freshness (`src/lib/query.ts`): every cache uses one of `FRESH.catalogue` (kept until the nightly sync's `data_stamp` moves; titles, people, lists), `FRESH.mine(...deps)` (the member's own things), `FRESH.logs` or `FRESH.live`. No timers per screen. After saving one of the member's own things on the server, call `changed('services' | 'watchlist' | 'letterboxd')`: every saved answer built from it is marked stale and the ones on screen reload quietly (Home rebuilds out of sight). The member's services are read through `useServicesQuery`/`useMyServices`, not a query of their own.
- Pull to refresh: on every page that shows server content and scrolls (Home, Title, Person, Watchlist, Browse and its pages); it comes with the page frame (`frame.pull`: `bind` on the <main>, `indicator` after it), and a page outside the frame uses `usePageRefresh(...queries)`. Not on pages where you type or change settings (Search, Settings and its pages, onboarding), fixed text (Privacy, Terms) or sheets: those opt out with `usePageFrame(page, { refresh: false })` or by not using it. A pull asks for the sync stamp, then reloads what the page shows past the saved copy (and the member's own things it is built from; Home rebuilds). It is the one time a page changes under the member's eyes. Offline or failing, the page stays as it is; the spinner shows at least 0.9 s and a second pull while busy does nothing. Pages never rely on it to be fresh.
- Pictures: posters use `Cover` (in `TitleCard`), wide pictures `NearImage`; a row of them that scrolls sideways is a `PosterRow` or `NearRow`. Each is asked for a screen and a half before it is seen and shows once decoded, with the same fade. No plain `<img loading="lazy">` for pictures in rows.
- Holding a poster: one menu for the app (`HoldProvider` in App). Poster cards open it themselves; a custom row uses `useHold`. Screens don't keep a menu or `held` state of their own.
- Leaving notes ("Leaves in 3 days") come from `leavingFor` in `src/lib/catalogue.ts`, with the screen's `stale` flag.
- Days: "today", "in 3 days" and the daily rotation are the phone's own calendar days (`src/lib/days.ts`: `localDay`, `daysUntil`, `dayNumber`), never UTC's (`toISOString().slice(0, 10)`).
- Pages and links: every page that loads content has one entry in `src/lib/pages.ts` (what it loads, its key, the pictures it waits for); the page reads through it (`usePageQuery`) and preloads through it (`warmPage`). Every link or button that opens a page is a `PageLink`, `PageButton` or `ViewAll` from `src/ui` (or spreads `usePageLink`), so the page starts loading on press. A new page that loads content gets an entry in `pageFor`. Off production, a page opened by a tap that wasn't preloaded logs a `[pages]` warning in the console.
- Row length: a row of posters shows only with at least `MIN_ROW` (7, in `catalogue.ts`) titles, on Home, Browse and the title page. Home rows fill up instead of shrinking: a title another row already shows can come again after a row's first 4 places, and the personal rows top up from `title_similar` (see `home_because`/`home_saved`/`home_people`).
- Explore (`src/lib/explore.ts`, `Explore` in Browse.tsx): a Browse list made of filters (genre, decade, country, length, leaving, new) opens with those filters as chips that can be taken off (Country is a drawer row where the database filters: Search and Explore, `SERVER_ROWS`), the heading follows the chips (`exploreTitle`), and the list is read from the database by its filters a page at a time with real totals (`exploreOf` decides; lists with any other rule, such as Trending, Hidden gems or Award winners, stay a fixed grid). Browse › All titles (`/browse/titles`) is the same page with nothing set. Decades can be picked several at once (`Draft.decades`).
- View all: a row offers it only when its full list has more than the row shows. Home rows set it through `row()` in `src/lib/home.ts` (a target and the list the row was taken from); the lists behind Home's rows are Browse categories in the hidden `home` section. Don't add View all links by hand.
- Start-up code: screens Home doesn't need at launch are `lazy` in App (wrapped in `Later`); keep new screens that way. The app's Supabase client is `src/lib/supabase.ts` (auth-js + postgrest-js only); don't add `@supabase/supabase-js` back to the app.
- Rating in queries: sort or narrow by `titles.imdb_rating` / `titles.imdb_votes` (copies of the scores kept by a trigger, indexed), never by `scores!inner` (that joins and sorts every title). Run the `Database size` workflow to see sizes, index use and the slowest queries. Keep nightly writes to what really changed (an update copies the whole row): popularity is written only when it moves 15%. `Database compact` (by hand) rewrites the busiest catalogue tables without the empty space updates leave; first run 24 Nov took the database from 170 to 122 MB.
- Tests: browser tests in `tests/e2e` run the built app against a mock Supabase: run them before every push to `sprint-2` (`docs/testing.md`); on GitHub the `Browser tests` workflow runs them, with lint and the vercel.json check, on the pull request that merges app code into `main`, before it is merged (to keep within the 2,000 free Actions minutes a month; the nightly sync uses most of the rest). New behaviour gets a test; new data a screen reads gets a mock in `mock_api.py`.
- Errors: a screen that fails to draw shows "Something went wrong" (`Crashed`, around App) and every uncaught error is reported to `client_errors` (`src/lib/errors.ts`; 30 days; the Database size workflow lists them).
- Saved data on the phone is pruned (`prune` in query.ts): nothing unused for 30 days, at most the newest 400 entries.
- Lint: oxlint with the React Compiler-style rules (refs, set-state-in-effect, immutability, purity, only-export-components) off, as the app uses those patterns on purpose (latest-value refs, screens exporting helpers); `npm run lint` should print nothing.
- UI copy is English for now; Swedish copy is decided in the Supabase phase.
